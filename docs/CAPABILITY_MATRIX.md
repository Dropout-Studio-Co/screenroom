# Platform capability matrix

> **2026-10-27:** platforms reduced to the three Personal Edition targets by
> [ADR-004](ADR-004_PERSONAL_EDITION_SCOPE.md). Linux, LG webOS and Android TV
> columns are gone; the Flutter-era matrix is history.

**Legend**
`core` = implemented in `screenroom-core` and covered by host tests ·
`host` = implemented and exercised in the running application on this macOS host ·
`—` = not built yet ·
`BLOCKED` = needs hardware, tooling or credentials that are unavailable ·
`proven` = verified on the physical target device (none yet).

| Subtitle source priority and provider (F15) | core: a `subtitles` table (schema 8, additive, guarded by a table check) storing the **bytes the owner kept** with language, format and provenance; imports and downloads are bounded (4 MiB), text-only (a NUL sample is refused), limited to srt/smi/vtt/ass/ssa/sub/ttml/dfxp, and the language is reported as Unknown rather than guessed. The provider is **The Subtitle DB** and only that ([ADR-005](ADR-005_SUBTITLE_PROVIDER_AND_FEATURE_REMOVALS.md)): anonymous lookups by TMDB/IMDb id, release name and title, a keyed catalogue search, `/get/{id}` answering 302 to the file host, lookup 404 as a miss, download 404 as unavailable, 400/401 actionable, 429/503 retried with `Retry-After`, pages of 100, redirects limited to the TSDB hosts with `Authorization` stripped across hosts. Verified in the running installed app on 2026-11-03: a Bengali subtitle downloaded from TSDB was applied automatically, the picker showed `…srt · subrip`, and Bengali text was drawn over the picture with the cue changing with the playhead; after a restart with the provider pointed at a dead address the kept copy still applied and rendered with **no socket open**; and the panel at 640×480 is unclipped, with `↑`/`↓` and `Enter` operating it as well as the pointer. Detail, commands and screenshots: [`SUBTITLE_PROVIDER.md`](SUBTITLE_PROVIDER.md) §8 | — |

A `core` cell means the rule exists and is tested in Rust: it does **not** mean a
user interface exposes it. The `host` cells are the ones a person can actually
operate today, and only on macOS. A `client` cell is the TV client's TypeScript,
which is typechecked and covered by 180 off-device tests. Since 2026-10-28 the
client's bundle *does* execute on the television (the set reports a mounted
1920×1080 canvas and `avplay=1`), but executing is not the same as verified: no
frame has been seen, no drive walked and no media played there. A `client` cell
still never means "verified on the TV".

What is left, task by task and with its evidence, is
[`MACOS_REMAINING_WORK.md`](MACOS_REMAINING_WORK.md). This table says what a
capability can do; that one says what is missing and what would close it.

## Per-device capabilities that must never be assumed

Container extension ≠ codec support. 1080p UI coordinates ≠ 4K playback. A remote
image URL ≠ offline artwork. A USB drive on one device ≠ visible on another.
Picture-in-Picture is not offered on any device. DLNA ≠ every cast protocol. A successful scan ≠ correct
identity. A green unit test ≠ device acceptance. A screenshot of the owner's other
application ≠ Screenroom evidence.

Each of these is recorded per device as `supported`, `unsupported (reason)` or
`unverified` in the platform adapter — never as an optimistic default.
