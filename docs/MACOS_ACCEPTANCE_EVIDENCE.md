# macOS acceptance — automated evidence and what is left for a person

Session of **2026-11-01**, host Apple M4 MacBook Air (macOS, Command Line Tools
only), from `7dc9063`. Every runtime claim below was produced on this host in this
session; nothing is carried over, quoted from memory or inferred from a build.

The checklist itself is [`MACOS_ACCEPTANCE_CHECKLIST.md`](MACOS_ACCEPTANCE_CHECKLIST.md).
This document is the receipt for the parts of it an agent can actually execute.

## Method

The 15 steps were written on the assumption that each one needs a visible window,
a person's eyes or ears, or a drive in hand. Each step ends in such an
observation, but most of the *mechanism* underneath it fails in ways a person
would see rather than in ways a person would have to judge: Enter playing the
wrong episode is a focus bug, an arrow seek is a number in the player's own
read-back, resume after quitting is a row in SQLite.

So `apps/desktop/src/app/acceptance.rs` drives the **real application object** —
`App::update` with the same `Message` values the window delivers, the same
catalogue queries, the same scan thread, the same libmpv worker, the same
checkpoint policy and the same SQLite file — and observes the outcome. Media is
generated by FFmpeg into a temporary folder the test owns: a three-episode series,
a two-language film with two audio and two subtitle tracks, a 2:1 anamorphic film
at 1920×1080 storage with 9:8 pixels, and 1,200 placeholder files for the scan
walk. **The owner's drive was not mounted and was not opened**; nothing was
written outside temporary directories.

```bash
cargo test -p screenroom-desktop --lib acceptance -- --test-threads=1
```

**16 tests, 0 failures.** They are a normal part of `cargo test --workspace`, so
they run on every future change instead of once.

## Defects found and fixed

### 1. Arrow keys could not reach episode 3 of a short season (step 3) — High

`move_focus` stepped ↑/↓ by `self.columns()` on **every** screen, because that is
how the card grid moves a whole row. The Detail screen draws its episodes as a
single column, so on a 1,280-wide window the step was 4: with a three-episode
season, `current + 4 < 3` was false and **↓ did nothing at all**. The checklist
step "use ↑/↓ to pick episode 3, press Enter" was impossible from the keyboard in
exactly the case it describes. Enter then played the episode the screen opened on,
which is the failure the step was written to catch.

Fixed by stepping one row on the Detail list and the column count on grids
(`apps/desktop/src/app.rs`), with both halves asserted in
`down_the_episode_list_moves_one_episode_not_one_grid_row` — the list moves one
episode and stops at its end, the grid still moves a whole row.

### 2. Cards could not appear until a scan had finished (step 1) — Medium

`drain_scan` reported the walk but only reloaded the catalogue when the scan
*ended*, so on a folder that takes seconds to walk the grid stayed empty and then
filled in one jump. Step 1 asks for "cards appear before it finishes", and a
first run on a slow drive is where that matters. Fixed by refreshing Home and
Browse part-way through a walk at most every 500 ms — bounded, so a 250,000-entry
scan cannot become 250,000 catalogue reloads. Covered by
`step_1_a_first_run_scan_fills_the_grid_before_it_finishes` (1,200 real files)
and `step_1_a_mid_scan_report_refreshes_the_catalogue_before_the_walk_ends`.

Both defects were found by the acceptance work itself, not by inspection.

### 3. A preview sought blind, so a short clip never previewed (2026-11-01) — Medium

`Preview::start` loaded at `preview_position_ms(duration_ms)`, and a duration of 0
gives 30 s. A file shorter than 30 s therefore started **past its own end**: the
player ended, `drain_preview` released the preview, and the card kept its poster. It
only worked when the library row already carried a duration, which is why
`step_17_a_preview_is_one_delayed_decoder_and_reduced_motion_stops_it` alternated
between passing and failing and failed every time it ran alone.

Fixed by loading at the start and seeking once, in `Preview::tick`, only after
`snapshot.duration_ms()` is known, so the target is always inside the file. That
test now runs in 1.9–3.2 s instead of 15–16 s and passed 5 runs out of 5; the
workspace is 352 tests with 0 failures. Found while re-checking the 4K work, not by
inspection.

## Redundant work removed, and the 4K ceiling located (2026-11-01)

Two changes, each measured on its own, with the software renderer kept as the path.

**One copy fewer per frame.** `screenroom-player` used to ask libmpv to draw into its
own buffer and then copy that buffer into a pooled frame buffer — 33.2 MB of memcpy for
every 3840×2160 frame. libmpv now draws directly into the pooled buffer. The pool is
allocated with 64 bytes of slack and the frame records the alignment offset, because
`render.h` requires the `SW_POINTER` to be 64-byte aligned for its fast path; every
pooled pointer measured offset 0, so the fast path is the one taken. `Frame` gained
`offset` and a `bytes()` accessor, the texture upload starts at that offset, and a
release run still uploads exactly one texture per delivered frame.

**No redraw without a new picture.** iced redraws a window whenever any message
arrives, and the application ticked every 16 ms while a player existed — so it drew at
51.5/s for a 24 fps source. The tick now watches `Player::frame_ticks()`, an atomic the
worker bumps when it publishes a frame, and only produces a message on a new frame or
every 250 ms of idle. Interleaved release runs: **4K drawn 13.7–14.1/s** (delivered
11.9–12.4), **1080p drawn 29.9/s** (delivered 28.7). Playback, seeking, resume and
every other player control were exercised by the existing test suite plus the bundle
walkthrough; the mini player that this session also covered was removed on 2026-11-02
with the feature.

**The limit is mpv's CPU colour conversion.** `SCREENROOM_PLAYER_TRACE` puts
`mpv_render_context_render` at **41.0–41.2 ms** for a 3840×2160 frame, identical with
`SCREENROOM_HWDEC=no` and `auto-copy`, inside a 42 ms frame budget. mpv 0.41.0
documents the software API as CPU, single-threaded colour conversion, and accepts a
non-RGB `SW_FORMAT` only when it has one plane, so the conversion cannot be moved or
narrowed from this side. Removing the second copy therefore did not raise delivery
(interleaved A/B contained within noise) — it removed 33 MB of per-frame memory traffic
and left the pipeline with one copy, which is what the code now does.

**Not attempted, and recorded as the obstacle:** a GPU render path. There is no Metal
render API in libmpv; the only GPU option on macOS is `MPV_RENDER_API_TYPE_OPENGL`,
which needs an OpenGL context and an IOSurface-backed FBO, while iced presents through
wgpu/Metal. Bridging those requires a custom compositor, which is an architectural
change rather than a fix; no prototype was built and no speedup is claimed.

## The smallest remaining manual session

Ordered so the owner can stop early. Time is dominated by waiting, not by work.

1. `scripts/package-macos.sh && scripts/verify-bundle.sh`, then
   `open dist/Screenroom.app` (answers Gatekeeper's one-time prompt).
2. Add the SSD folder; **watch** whether the grid fills while the row counts up
   (step 1) and whether posters look like the right titles (step 2).
3. Open a series, press ↓ twice, Enter, and **listen** for a few seconds: is
   speech in sync (step 4's listening half)?
4. In that film: switch audio and subtitle language and confirm both change
   (step 5); press `f`, check the picture fills the display, leave it, and confirm
   the header returns and one Escape exits (step 6).
5. Play the 2:1 anamorphic film and confirm it looks wide, unstretched (step 7).
6. Play the 4K HEVC film on battery for five minutes: note the percentage before
   and after (step 8). This is the only step with a known open defect.
7. While it plays, **unplug the drive**: a clear failure and "unavailable" cards
   rather than a hang; replug and Rescan, and confirm it plays (step 12).
8. Run the keyboard-only journey and judge whether the focused card is readable
   (step 15).

Steps 9–11, 13 and 14 no longer need anything from a person: they are asserted
against the real application, its real database and a real player.
