# WS-6 — casting verification against a first-party test receiver (2026-11-21)

**Verdict: the casting code path is verified over real LAN sockets against
Screenroom's own test receiver. It is still unverified on any real device.**

This is not a third-party device test. No television, no VLC, no Kodi, no
upmpdcli and no other renderer took part. The receiver used here is first-party
code in `scripts/dev-receiver/`, written for this verification, and it says so in
its own name, log, status file and README. The F19 device gate therefore stays
where it was: closed until a receiver the owner owns answers a search and plays a
film.

- Branch: `verify/macos-casting`, forked from `origin/main` at `7ac4273`.
- Host: the owner's MacBook Air M4, macOS 27.2.1, arm64.
- Runs: four consecutive full verifications on 2026-11-21. The first (`run1`)
  failed one assertion because the runner demanded a `GetPositionInfo` the app
  never makes; the harness was corrected to read the position explicitly, and
  `run2`, `run3` and `run4` then passed every assertion identically. No casting
  defect was involved.

## 1. What was built

| File | Role |
| --- | --- |
| `scripts/dev-receiver/receiver.py` | Standalone MediaRenderer test double: SSDP on UDP 1900 with the multicast group joined, HTTP description and SCPD documents, AVTransport and RenderingControl SOAP, media pull with a range request, ffprobe self-check, JSON status, clean shutdown. Python 3 standard library only. |
| `scripts/dev-receiver/run-verification.sh` | Generates a rights-cleared clip, runs a full session and a dropped session, asserts every claim from the evidence files, prints one PASS/FAIL line per claim. |
| `scripts/dev-receiver/README.md` | How to run the receiver and the verification, and what the receiver deliberately refuses to do. |
| `apps/desktop/examples/cast_lan_probe.rs` | Drives `casting::discover` → `casting::describe` → `cast_stream::StreamServer::start` → `cast_session::connect`, then pause, seek, resume, stop and disconnect, recording state reads, endpoint behaviour and `lsof` output. |

No change to `casting.rs`, `cast_stream.rs` or `cast_session.rs` was needed: no
defect surfaced on the real path, so no regression test was added to them.

### Receiver design, in one paragraph

It binds UDP 1900 with `SO_REUSEADDR`/`SO_REUSEPORT`, joins 239.255.255.250 on the
advertised interface, and answers an M-SEARCH for
`urn:schemas-upnp-org:device:MediaRenderer:1` from a second socket bound to the
LAN address, so the reply's source IP and the `LOCATION` host agree. `LOCATION`
points at `http://<lan>:<port>/desc.xml`, which lists `AVTransport:1` and
`RenderingControl:1` with absolute control and SCPD URLs — exactly the shape
`casting::parse_description` and `resolve_url` accept. On `Play` it fetches the
`CurrentURI` the app published with `Range: bytes=0-`, requires HTTP 206 (200 is
also accepted but recorded honestly), writes the bytes to a temp file, runs
`ffprobe` over them, and only then reports `PLAYING`. A failed fetch becomes SOAP
fault 716 and the transport goes to `STOPPED` instead of pretending. Positions
advance from a monotonic clock while playing, freeze on pause, and jump on seek.

## 3. Session transcript

Source clip: 2,015,964 bytes, 20.000 s, 640×360 H.264 + AAC in MP4 (`mov,mp4`),
generated by `ffmpeg` lavfi from `testsrc2` and a sine tone. No private media was
read.

The app drove every call; the receiver's own log is the second witness.

| Step | App call | App readback | Receiver side |
| --- | --- | --- | --- |
| 1 | `casting::discover(3 s, 12)` | 1 receiver: `Screenroom Test Receiver (first-party)`, kind `DLNA MediaRenderer`, `http://192.168.0.x:56110/desc.xml`, answered from `192.168.0.x` | `ssdp answered a urn:schemas-upnp-org:device:MediaRenderer:1 search` |
| 2 | `casting::describe` | friendly name `Screenroom Test Receiver (first-party)`; two services, AVTransport and RenderingControl, both control and SCPD URLs resolved | `http GET /desc.xml`, `http GET /AVTransport.xml`, `http GET /RenderingControl.xml` |
| 3 | `cast_stream::StreamServer::start` (direct) | 206 for `bytes=0-`, 2,015,964 body bytes | not involved (this is the app's endpoint) |
| 4 | `cast_session::connect` → `SetAVTransportURI` + `Play` | state `playing` on first read | `SetAVTransportURI`, `Play`, then `fetched 2015964 bytes with HTTP 206` and `ffprobe accepted the fetched file` |
| 5 | `CastSession::pause` | `paused` | `Pause` then `GetTransportInfo` → `PAUSED_PLAYBACK` |
| 6 | `CastSession::seek(10 s)` | `paused` | `Seek` → `GetTransportInfo` → `PAUSED_PLAYBACK` |
| 7 | receiver `GetPositionInfo` (probe, to read the position the app cannot read) | `RelTime 00:00:10` on HTTP 200 | position held at the seek target while paused |
| 8 | `CastSession::resume` | `playing` | `Play` → `GetTransportInfo` → `PLAYING` |
| 9 | receiver `GetPositionInfo` again | `00:00:10` (0.6 s later, truncated to seconds) | advancing from the seek target |
| 10 | `CastSession::stop` | `stopped` | `Stop` → `GetTransportInfo` → `STOPPED` |
| 11 | `CastSession::disconnect` | `Ok(())`, stream already closed | — |

App-facing summary after stop, verbatim from `CastSession::summary()`:

> The stream to Screenroom Test Receiver (first-party) is closed, so this casting
> session is over. The receiver last reported stopped.

Receiver action counters for the session: `SetAVTransportURI` 1, `Play` 2,
`Pause` 1, `Seek` 1, `Stop` 1, `GetTransportInfo` 5, `GetPositionInfo` 2. Final
state `STOPPED`, duration 20.0 s.

## 4. The fetched bytes are the same media

The receiver pulled the app's tokenized URL itself, with a range request, and
probed what it received:

```
fetched    HTTP 206, Content-Range: bytes 0-2015963/2015964, 2015964 bytes
ffprobe    mov,mp4,m4a,3gp,3g2,mj2
           h264 640x360, aac, duration 20.0s, size 2015964
source     mov,mp4,m4a,3gp,3g2,mj2
           h264 640x360, aac, duration 20.0s, size 2015964
```

Byte count, container, both codec names, dimensions and duration all match the
source. The receiver also refused nothing: `ffprobe` exited 0 on the pulled file.

## 5. Endpoint confinement

Both the probe's direct `StreamServer` and the session's own endpoint were probed
with the same four requests:

| Request | Direct endpoint | Session endpoint |
| --- | --- | --- |
| `GET /stream/<token>` with `Range: bytes=0-` | 206, `bytes 0-2015963/2015964`, 2,015,964 bytes | 206, same header, same length |
| `GET /` | 404 | 404 |
| `GET /library` | 404 | 404 |
| `GET /stream/not-the-token` | 404 | 404 |

So the endpoint serves exactly one opaque path, serves the whole file once, and
exposes no library or listing surface. That matches the existing unit tests and
now also holds over a real TCP connection from the receiver's side.

## 6. Listener-close proof

Same process, same `lsof`, before and after the stop. Addresses are redacted to
their last octet in this document; the unredacted lines are in the local evidence
directory only.

While streaming:

```
cast_lan_ 82453 beyourahi 3u IPv4 0xdf347ee71cb1c579 0t0 TCP 192.168.0.x:56126 (LISTEN)
```

After `CastSession::stop` and `disconnect`, `lsof -nP -a -p 82453 -i` produced no
lines at all (`"listeners_after_stop": []`, `"listener_closed": true`). The direct
endpoint shows the same pair: one `LISTEN` on `192.168.0.x:56120` before
`StreamServer::stop()`, nothing after.

The receiver's own listener closed too: `lsof -nP -iTCP:56110` was empty once the
process exited, and its status file records `"listening": false` with a close
timestamp. Its log ends:

```
shutdown requested
ssdp listener closed
http listener closed; receiver stopped
```

## 7. Dropped connection

Second run: the session was started normally (`playing`), then the receiver process
was killed with `SIGTERM` mid-session, then the app called `refresh()`.

- App result: `Err`, text
  `Cannot reach the receiver at 192.168.0.x:56148: Connection refused (os error 61)`
  (last octet redacted here; the process printed the full address locally).
- App state afterwards: `unreported (Cannot reach the receiver at 192.168.0.x:56148:
  Connection refused (os error 61))`.
- Stream endpoint after the failure: `is_streaming()` false, and `lsof` empty — the
  `settle()` path closed the listener without any further call.
- Receiver listener: closed (process gone), port not listening.

That is the "clear failure and no leak" outcome, not a silent hang and not a
stream still open to a receiver that no longer exists.

## 8. Token hygiene

The probe wrote the session token to a private file under the evidence directory,
the runner grepped eight artefacts for it, then deleted the file. The token was
absent from: the probe's stdout log, the receiver log, the receiver status JSON,
the dropped-session logs, both status files and both evidence JSON files — zero
occurrences in every file. Everything the runner prints and everything committed
carries `http://192.168.0.x:<port>/stream/<redacted>` instead.

The receiver redacts the stream path in its log and status before writing them, so
a receiver bug cannot leak the token into a shared file either.

## 9. What this does not prove

- **No real device.** No third-party renderer, television or set-top box has
  answered a search or played a frame. The test receiver is first-party code.
- **One machine.** App and receiver were separate processes with real UDP and TCP
  sockets on `192.168.0.x`, but on the same host, so the Wi-Fi hop, a second
  machine's ARP/firewall behaviour and multicast snooping on a TV were not
  exercised. A remote device test is still required.
- **No eventing.** The app does not subscribe, and the receiver does not implement
  `SUBSCRIBE`; transport state is polled, which is what the app does.
- **No transcoding, no DRM, no protected media.** The clip is generated H.264/AAC.
- **No Windows or Tizen run.** Both remain deferred by ADR-004 and this session did
  not touch them.

## 10. Recommended capability text (for the integrator)

`casting::CAPABILITY_TEXT` today says the path "has only been run against an
in-process fake receiver: no real device has ever played anything through it, and
no receiver has answered a search on this network either". The first and third
clauses are now false — a receiver answered and played. Recommended replacement,
same shape, still refusing to claim a device:

```text
A casting session can describe a receiver, serve one chosen file from a temporary endpoint that
closes itself, and send AVTransport controls. On 2026-11-21 the whole path ran over real LAN
sockets against Screenroom's own test receiver in scripts/dev-receiver: discovery found it, pause,
seek, resume and stop each read back, and the receiver fetched the served file with a 206 that
ffprobe accepted as the same media. That receiver is a first-party test double, not a device: no
real device has ever answered a search or played anything through this path, so casting stays
unverified on hardware until a receiver you own answers and you watch a film play on it.
```

That text is asserted by `casting::tests::the_capability_text_never_claims_a_verified_receiver`,
which currently requires the literal phrases `fake receiver`,
`no real device` and `no receiver has answered a search`. The recommended text keeps
`no real device` but drops the other two, so the test must change in the same
commit — its checks become:

```rust
assert!(!capability.verified_on_a_receiver);
assert!(CAPABILITY_TEXT.contains("test receiver"));
assert!(CAPABILITY_TEXT.contains("no real device has ever answered a search"));
assert!(!CAPABILITY_TEXT.contains("works with"));
```

Keep `Capability::verified_on_a_receiver` at `false`. A first-party test double is
not a device verification, and the flag is the one bit the UI uses to decide
whether it may imply otherwise.

Suggested F19 row wording (matrix, backlog and gates are integrator-owned and were
not edited):

> **Session path verified against the first-party test receiver** (2026-11-21,
> `verify/macos-casting`): SSDP discovery, description, session-scoped 206 stream,
> AVTransport play/pause/seek/resume/stop state readback, drop recovery and
> listener close all run over real sockets; the receiver's fetched bytes ffprobe as
> the source. **Device gate still closed:** no third-party renderer has answered or
> played; P1-08 stays open.
